## Docker in Docker (DinD), а также Docker outside the Docker (DooD)

### **Docker in Docker (DinD): Docker внутри Docker-контейнера**

*   **Описание:** DinD подразумевает запуск полноценного Docker daemon *внутри* Docker-контейнера.  То есть, у вас есть Docker Engine, работающий на хост-машине, и еще один Docker Engine, работающий внутри контейнера, который выполняет job'ы GitLab CI/CD.
*   **Принцип работы:** Docker executor запускает контейнер, который содержит Docker daemon.  Когда ваш job выполняет команды `docker build`, `docker push` и т.д., эти команды выполняются *внутри* контейнера DinD, обращаясь к Docker daemon *внутри этого контейнера*.
*   **Схема:**

    ```
    +-----------------------+
    | Хост-машина (Runner) |
    +-----------------------+
    |   Docker Engine       |
    |   +-----------------+ |
    |   | Runner Container  |   
    |   |   +-----------+   |   
    |   |   | DinD      |   |   
    |   |   | Container |   |   
    |   |   |  Docker   |   |   
    |   |   |  Daemon   |   |   
    |   |   +-----------+   |   
    |   +-----------------+ |
    +-----------------------+
    ```

*   **Преимущества:**
    *   **Изоляция:**  Контейнер DinD полностью изолирован от хост-машины. Любые изменения, сделанные внутри контейнера, не повлияют на хост-систему.
    *   **Чистота:**  После завершения job'а контейнер DinD уничтожается, оставляя хост-машину в исходном состоянии.
    *   **Безопасность:** Меньше риска скомпрометировать хост-машину.

*   **Недостатки:**
    *   **Производительность:**  Более ресурсоемкий, так как запускается еще один Docker daemon. Дополнительные накладные расходы на виртуализацию.
    *   **Сложность:**  Требуется настройка привилегированного режима (`privileged = true`) для запуска Docker daemon внутри контейнера.
    *   **Persistent Storage:**  Сложности с использованием постоянного хранилища для Docker volumes.
*   **Использование в GitLab CI/CD:**

    ```yaml
    stages:
      - build

    build_image:
      stage: build
      image: docker:stable  # Образ с Docker CLI
      services:
        - docker:dind  # Запускаем DinD service - Docker Daemon
      variables:
        DOCKER_TLS_CERTDIR: "" # Отключаем TLS (для простоты) - **ВНИМАНИЕ: В Production не рекомендуется отключать TLS**
      script:
        - docker build -t my-image .
        - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
        - docker push "$CI_REGISTRY_IMAGE/my-image:$CI_COMMIT_SHA"
    ```
    *   `image: docker:stable`: Использует образ с Docker CLI (командная строка).
    *   `services: - docker:dind`: Указывает, что нужно запустить DinD service. GitLab CI/CD автоматически настроит его.
    *   `DOCKER_TLS_CERTDIR: ""`:  Отключает TLS (транспортный уровень безопасности) для упрощения настройки. **Не рекомендуется отключать в production окружении!**

    По частям:
    
    ### 1. **Docker-in-Docker (DinD) сервис**
```yaml
services:
  - name: docker:dind
    alias: thedockerhost
    command: [ '--tls=false' ]
```
- **DinD** (`docker:dind`) позволяет запустить Docker-демон внутри контейнера, который используется для сборки образов.
- Это необходимо, потому что базовый образ `docker:stable` содержит только Docker-клиент, но не демон.
- `alias: thedockerhost` задаёт псевдоним для обращения к этому сервису.
- `--tls=false` отключает TLS для упрощения подключения (в продакшене это не рекомендуется).

### 2. **Настройка переменных для работы с DinD**
```yaml
variables:
  DOCKER_HOST: "tcp://thedockerhost:2375/"
  DOCKER_DRIVER: "overlay2"
  DOCKER_TLS_CERTDIR: ""
```
- `DOCKER_HOST` указывает Docker-клиенту, что нужно подключаться к DinD-сервису по адресу `thedockerhost:2375`.
- `DOCKER_TLS_CERTDIR: ""` отключает TLS (так как DinD запущен с `--tls=false`).

### 3. **Базовый образ `docker:stable`**
```yaml
image: docker:stable
```
- Это лёгкий образ с установленным Docker-клиентом, который позволяет выполнять команды `docker build`, `docker push` и т.д.

### 4. **Зачем вся эта конструкция?**
- GitLab CI/CD запускает каждый job в изолированном окружении (контейнере).
- Чтобы в этом окружении можно было собирать Docker-образы, нужно:
  1. **Docker-клиент** (`docker:stable` в `image`).
  2. **Docker-демон** (DinD в `services`).
- Таким образом, DinD выступает как "удалённый" Docker-демон, а клиент в основном контейнере отправляет ему команды.

**Docker-outside-of-Docker (DooD): Docker за пределами Docker-контейнера (Использование Docker Socket)**

*   **Описание:** DooD подразумевает использование Docker daemon, запущенного *на хост-машине*, изнутри Docker-контейнера. Контейнер монтирует сокет Docker daemon хоста (`/var/run/docker.sock`) внутрь себя.
*   **Принцип работы:** Docker executor запускает контейнер.  Вместо запуска нового Docker daemon внутри контейнера, команды `docker build`, `docker push` и т.д. выполняются, обращаясь к Docker daemon *на хост-машине* через смонтированный сокет.
*   **Схема:**

    ```
    +-----------------------+
    | Хост-машина (Runner) |
    +-----------------------+
    |   Docker Engine      |
    |   +-----------------+|
    |   | Runner Container |  |
    |   |   Docker CLI     |  |
    |   |   +---------->   |  |  -- Socket
    |   +-----------------+   |
    +-----------------------+
    ```

*   **Преимущества:**
    *   **Производительность:**  Меньше накладных расходов, так как не нужно запускать дополнительный Docker daemon.
    *   **Проще в настройке (иногда):** Не требует привилегированного режима.

*   **Недостатки:**
    *   **Безопасность:**  Самый главный недостаток - значительно снижена безопасность. Контейнер получает доступ к Docker daemon хоста, и потенциальные уязвимости в job'е могут скомпрометировать хост-машину.
    *   **Ограничения:**  Не все операции, требующие определенных прав доступа, могут быть выполнены.
    *   **Сложность управления доступом:**  Трудно ограничить права доступа контейнера к Docker daemon хоста.
*   **Использование в GitLab CI/CD:**

    ```yaml
    stages:
      - build

    build_image:
      stage: build
      image: docker:latest
      variables:
        DOCKER_HOST: tcp://docker:2375  # Или unix:///var/run/docker.sock (требует настроек безопасности!)
      script:
        - docker build -t my-image .
        - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
        - docker push "$CI_REGISTRY_IMAGE/my-image:$CI_COMMIT_SHA"
    ```

    В этом примере вам нужно настроить Docker Engine для прослушивания входящих подключений на порту 2375 (что *очень* небезопасно) или использовать Unix socket (`/var/run/docker.sock`). **DooD крайне не рекомендуется использовать в production.**

**Сравнение DinD и DooD:**

| Feature       | DinD (Docker in Docker) | DooD (Docker-outside-of-Docker) |
|---------------|--------------------------|---------------------------------|
| Изоляция      | Высокая                  | Низкая                           |
| Безопасность   | Высокая                  | Низкая                           |
| Производительность | Ниже                   | Выше                            |
| Сложность     | Выше                   | Ниже                            |
| Привилегии    | Требуются               | Обычно нет                      |

**Когда использовать DinD vs DooD:**

*   **DinD:** Используйте, когда нужна изоляция и безопасность превыше производительности. Это *рекомендуемый* подход для большинства случаев. GitLab CI/CD упрощает настройку DinD с помощью `services: - docker:dind`.
*   **DooD:** *Избегайте DooD в production.* Используйте только в крайних случаях, когда производительность критична, а вопросы безопасности не так важны (например, в изолированных средах разработки) и вы полностью понимаете риски.  Особенно если запускаете Runner'ы на публичных облачных платформах, DooD может создать серьезные проблемы с безопасностью.

**Безопасность (Важно!):**

*   **Никогда не предоставляйте неограниченный доступ к Docker daemon.**
*   **Всегда используйте TLS, если используете сетевой доступ к Docker daemon.**
*   **Рассмотрите использование Docker Contexts для ограничения доступа к Docker daemon.**
*   **По возможности, используйте DinD для обеспечения изоляции и безопасности.**
