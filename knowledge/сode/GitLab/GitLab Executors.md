## GitLab Runner Executor

**GitLab Runner Executors: Подробный Обзор**

Executor определяет, *как* GitLab Runner будет выполнять ваши CI/CD job'ы. Он создает среду, в которой будет запущен ваш код, и предоставляет механизмы для изоляции, управления зависимостями и доступа к ресурсам.

**1. Shell Executor:**

*   **Описание:** Самый простой executor. Он запускает job'ы непосредственно на хост-машине, где установлен GitLab Runner, используя системную оболочку (bash, zsh, PowerShell и т.д.).
*   **Преимущества:**
    *   Легко настроить: Не требует виртуализации или контейнеризации.
    *   Быстрый:  Нет накладных расходов на создание виртуальных сред.
*   **Недостатки:**
    *   Нет изоляции: Job'ы могут влиять друг на друга и на хост-систему.
    *   Конфликты зависимостей:  Разные job'ы могут требовать разные версии одного и того же программного обеспечения.
    *   Безопасность:  Уязвимости в job'ах могут скомпрометировать хост-машину.
    *   Сложность воспроизведения: Окружение job'а зависит от конфигурации хост-машины, что может привести к невоспроизводимым результатам.
*   **Подходящие Сценарии:**
    *   Простые проекты, где изоляция не критична.
    *   Среды разработки, где скорость важнее изоляции.
    *   Job'ы, которые требуют доступа к специфическим ресурсам хост-машины (например, USB-устройствам).
*   **Конфигурация (config.toml):**

    ```toml
    [[runners]]
      name = "My Shell Runner"
      url = "https://gitlab.example.com/"
      token = "YOUR_RUNNER_TOKEN"
      executor = "shell"
      shell = "bash"  # или "powershell", "zsh", и т.д.
    ```
*   **Схема:**

    ```
    +-----------------------------+
    | Хост-машина (Runner)         |
    +-----------------------------+
    |   GitLab Runner              |
    |   (Shell Executor)           |
    |   +---------------------+    |
    |   | Job 1:               |    |
    |   |   (Script исполняется  |    |
    |   |    непосредственно    |    |
    |   |    на хосте)          |    |
    |   +---------------------+    |
    |   +---------------------+    |
    |   | Job 2:               |    |
    |   |   ...                |    |
    |   +---------------------+    |
    +-----------------------------+
    ```

**2. Docker Executor:**

*   **Описание:** Каждый job выполняется в изолированном Docker-контейнере.  Указываете образ Docker (с помощью `image:` в `.gitlab-ci.yml`) для создания среды.
*   **Преимущества:**
    *   Изоляция: Job'ы не влияют друг на друга и на хост-систему.
    *   Воспроизводимость:  Окружение job'а определяется Docker-образом, что обеспечивает воспроизводимые результаты.
    *   Управление зависимостями:  Зависимости устанавливаются внутри Docker-образа.
    *   Портативность:  Docker-образы могут быть запущены на любой системе с Docker Engine.
*   **Недостатки:**
    *   Требуется Docker Engine на хост-машине.
    *   Накладные расходы на создание и запуск Docker-контейнеров.
    *   Сложность доступа к ресурсам хост-машины (нужно использовать volume mounts).
*   **Подходящие Сценарии:**
    *   Большинство проектов CI/CD.
    *   Проекты, требующие сложного окружения с множеством зависимостей.
    *   Проекты, где важна воспроизводимость и изоляция.
*   **Конфигурация (config.toml):**

    ```toml
    [[runners]]
      name = "My Docker Runner"
      url = "https://gitlab.example.com/"
      token = "YOUR_RUNNER_TOKEN"
      executor = "docker"
      image = "ubuntu:latest"  # Образ по умолчанию (если не указан в .gitlab-ci.yml)
      privileged = false  # Необходимо для DinD
    ```
*   **Схема:**

    ```
    +-----------------------------+
    | Хост-машина (Runner)         |
    +-----------------------------+
    |   Docker Engine              |
    |   +---------------------+    |
    |   | GitLab Runner       |    |
    |   | (Docker Executor)   |    |
    |   |   +---------------+ |    |
    |   |   | Job 1:        | |    |
    |   |   |   (Docker     | |    |
    |   |   |    контейнер) | |    |
    |   |   +---------------+ |    |
    |   |   +---------------+ |    |
    |   |   | Job 2:        | |    |
    |   |   |   (Docker     | |    |
    |   |   |    контейнер) | |    |
    |   |   +---------------+ |    |
    |   +---------------------+    |
    +-----------------------------+
    ```
*   **Пример .gitlab-ci.yml:**

    ```yaml
    stages:
      - build

    build_job:
      stage: build
      image: node:16  # Используем образ Node.js
      script:
        - npm install
        - npm run build
    ```

**3. Kubernetes Executor:**

*   **Описание:** Каждый job запускается как Pod в Kubernetes кластере.  Использует ресурсы Kubernetes для динамического выделения ресурсов и масштабирования.
*   **Преимущества:**
    *   Масштабируемость:  Автоматическое масштабирование Runner'ов в зависимости от нагрузки.
    *   Отказоустойчивость:  Kubernetes обеспечивает автоматическое восстановление Pod'ов в случае сбоя.
    *   Динамическое выделение ресурсов:  Каждый job получает необходимые ресурсы (CPU, память) из Kubernetes кластера.
    *   Интеграция с Kubernetes:  Можно использовать все возможности Kubernetes для управления окружением job'а.
*   **Недостатки:**
    *   Самый сложный в настройке:  Требует Kubernetes кластер и знание Kubernetes.
    *   Накладные расходы на управление Kubernetes кластером.
*   **Подходящие Сценарии:**
    *   Крупные проекты с высокими требованиями к масштабируемости и отказоустойчивости.
    *   Проекты, требующие сложного окружения с интеграцией с Kubernetes.
*   **Конфигурация (config.toml):**

    ```toml
    [[runners]]
      name = "My Kubernetes Runner"
      url = "https://gitlab.example.com/"
      token = "YOUR_RUNNER_TOKEN"
      executor = "kubernetes"
      namespace = "gitlab-runner" # Namespace, где будут создаваться Pod'ы
      service_account = "gitlab-runner" # Service Account для доступа к Kubernetes API
    ```
    * Требуется настроить доступ GitLab Runner к Kubernetes API.
*   **Схема:**

    ```
    +-----------------------------+
    | Kubernetes Cluster          |
    +-----------------------------+
    |   +---------------------+    |
    |   | GitLab Runner        |   |
    |   | (Kubernetes Executor)|   |
    |   |   +---------------+ |    |
    |   |   | Job 1:        | |    |
    |   |   |   (Kubernetes | |    |
    |   |   |    Pod)       | |    |
    |   |   +---------------+ |    |
    |   |   +---------------+ |    |
    |   |   | Job 2:        | |    |
    |   |   |   (Kubernetes | |    |
    |   |   |    Pod)       | |    |
    |   |   +---------------+ |    |
    |   +---------------------+    |
    +-----------------------------+
    ```
*   **Пример .gitlab-ci.yml:**

    ```yaml
    stages:
      - build

    build_job:
      stage: build
      image: alpine/git  # Базовый образ с git
      script:
        - git clone https://gitlab.example.com/my-project.git
        - cd my-project
        - make build
    ```

**4. Другие Executors (Кратко):**

*   **VirtualBox:** Job'ы запускаются в виртуальных машинах VirtualBox. Обеспечивает изоляцию, но требует установки VirtualBox на хост-машине.
*   **SSH:** Runner подключается к удаленному серверу по SSH и выполняет там job'ы. Полезно для развертывания приложений на удаленных серверах.
*   **Custom:** Позволяет создать свой собственный executor, который интегрируется с вашей инфраструктурой.

**Выбор подходящего Executor:**

*   **Shell:** Для простых проектов и тестирования.
*   **Docker:** Для большинства проектов CI/CD.
*   **Kubernetes:** Для крупных проектов с высокими требованиями к масштабируемости.
*   **VirtualBox:** Для проектов, требующих полной изоляции (но менее масштабируемый, чем Kubernetes).
*   **SSH:** Для развертывания на удаленных серверах.
*   **Custom:** Когда ни один из стандартных executors не подходит.

Надеюсь, это дает полное представление о GitLab Runner Executors!
