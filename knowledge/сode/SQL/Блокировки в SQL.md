# Блокировки в SQL: подробный обзор
## Основные типы блокировок
Блокировки — это механизм, который SQL-серверы используют для управления параллельным доступом к данным и поддержания целостности транзакций.

### 1. По режиму доступа

| Тип блокировки | Описание | Совместимость |
|---------------|----------|---------------|
| **Shared (S)** | Для операций чтения. Несколько транзакций могут одновременно удерживать S-блокировки на одном ресурсе. | Совместима с другими S-блокировками |
| **Exclusive (X)** | Для операций записи. Дает эксклюзивный доступ к данным. | Не совместима ни с какими другими блокировками |
| **Update (U)** | Промежуточная блокировка для операций, которые сначала читают, а потом могут обновлять данные. | Совместима с S, но не с другими U или X |

### 2. По уровню гранулярности

| Уровень блокировки | Описание | Когда используется |
|--------------------|----------|-------------------|
| **Блокировка строки** | Блокируется только одна строка таблицы | Наиболее распространенный тип, минимизирует блокировки |
| **Блокировка страницы** | Блокируется страница данных (обычно 8КБ) | Когда СУБД работает со страницами, а не отдельными строками |
| **Блокировка таблицы** | Блокируется вся таблица | Для массовых операций или когда нужна высокая согласованность |
| **Блокировка базы данных** | Блокируется вся БД | Для операций обслуживания БД |

### 3. По уровню детализации
- **Строки** (наиболее частый случай)
- **Страницы/Индексы**
- **Целиком таблицы**
- **Базы данных**

## Явные блокировки в SQL
### В PostgreSQL, MySQL, Oracle

```sql
-- Блокировка строк для обновления (X-блокировка)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- Блокировка строк для чтения (S-блокировка)
SELECT * FROM accounts WHERE id = 1 FOR SHARE;

-- Блокировка с пропуском заблокированных строк (NOWAIT)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;

-- Блокировка с ожиданием в течение указанного времени (SKIP LOCKED)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE SKIP LOCKED;
```

## Неявные блокировки

СУБД автоматически устанавливает блокировки при выполнении операций:
- `INSERT`, `UPDATE`, `DELETE` — X-блокировки на изменяемые строки
- `SELECT` — обычно не требует блокировок, но зависит от уровня изоляции
- Индексные операции — блокировки соответствующих индексных структур


## Deadlock (Взаимная блокировка)

Пример deadlock:
```sql
-- Транзакция 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- Ждет блокировки для id=2

-- Транзакция 2
BEGIN;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
UPDATE accounts SET balance = balance - 100 WHERE id = 1; -- Блокирует Транзакцию 1
-- Теперь Транзакция 2 ждет блокировки для id=1, которую удерживает Транзакция 1
```

СУБД автоматически обнаруживает deadlock и прерывает одну из транзакций (жертву deadlock).

## Оптимизация блокировок

1. **Сокращайте время транзакций** — чем быстрее транзакция, тем меньше времени удерживаются блокировки
2. **Используйте правильный уровень изоляции** — не используйте Serializable без необходимости
3. **Упорядочивайте доступ к ресурсам** — если все транзакции обращаются к таблицам/строкам в одном порядке, deadlock маловероятен
4. **Используйте `NOWAIT` или `SKIP LOCKED`** для неблокирующего чтения
5. **Разделяйте большие транзакции** на несколько меньших

## Особенности в разных СУБД

1. **PostgreSQL**:
   - Использует MVCC (Multiversion Concurrency Control)
   - Блокировки строк очень эффективны
   - `FOR UPDATE` блокирует только конкретные строки

2. **MySQL (InnoDB)**:
   - Использует индексные записи для блокировок строк
   - Имеет gap locks в Repeatable Read для предотвращения фантомов
   - `FOR UPDATE` может блокировать диапазоны при отсутствии подходящего индекса

3. **SQL Server**:
   - Богатая система хинтов блокировок
   - Поддерживает блокировки на уровне разделов таблицы
   - Имеет дополнительные типы блокировок (например, intent locks)

4. **Oracle**:
   - Использует MVCC
   - `FOR UPDATE` блокирует строки до конца транзакции
   - Минимальные блокировки чтения благодаря механизму undo-данных


## ⚔️ Пессимистичные vs Оптимистичные

### Пессимистичные блокировки (Pessimistic)
**Принцип**: "Лучше заблокировать, чем потом чинить"  
**Как работает**:
- Блокирует данные **до** изменения
- Гарантирует отсутствие конфликтов
- Пример:
  ```sql
  BEGIN;
  SELECT * FROM orders WHERE id = 5 FOR UPDATE; -- Блокировка!
  UPDATE orders SET status = 'paid' WHERE id = 5;
  COMMIT;
  ```
**Плюсы**:  
- Нет конфликтов при записи  
**Минусы**:  
- Может вызывать очереди и дедлоки

### Оптимистичные блокировки (Optimistic)
**Принцип**: "Проверим конфликт только при коммите"  
**Как работает**:
- Не блокирует данные при чтении
- Проверяет версию/таймстамп при обновлении
- Пример:
  ```sql
  -- Добавляем версию
  ALTER TABLE products ADD COLUMN version INT DEFAULT 0;
  
  -- Обновление с проверкой
  UPDATE products 
  SET price = 200, version = version + 1 
  WHERE id = 1 AND version = 5; -- Проверка исходной версии
  ```
**Плюсы**:  
- Высокая параллельность  
**Минусы**:  
- Нужно обрабатывать ошибки конфликтов
- Частые откаты при высокой конкуренции

## 🏆 Когда что использовать
- **Пессимистичные** — для критичных данных с высокой конкуренцией на запись
- **Оптимистичные** — для read-heavy систем или когда конфликты редки
