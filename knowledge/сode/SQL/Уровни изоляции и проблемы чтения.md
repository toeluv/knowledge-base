# Уровни изоляции транзакций и проблемы чтения

Транзакция - это последовательность операций с базой данных, которая рассматривается как единое целое. Транзакции обеспечивают целостность данных даже в случае сбоев системы.

### Свойства транзакций (ACID)

1. **Atomicity (Атомарность)** - транзакция выполняется полностью или не выполняется вообще
2. **Consistency (Согласованность)** - транзакция переводит базу данных из одного согласованного состояния в другое
3. **Isolation (Изолированность)** - параллельные транзакции не влияют друг на друга
4. **Durability (Долговечность)** - результаты успешно завершенной транзакции сохраняются даже после сбоев

### Уровни изоляции транзакций

1. **Read Uncommitted (Чтение неподтвержденных данных)**:
   - Самая слабая изоляция
   - Возможны "грязные" чтения (чтение незафиксированных изменений других транзакций)

2. **Read Committed (Чтение подтвержденных данных)**:
   - Запрещает "грязные" чтения
   - Но возможны неповторяющиеся чтения (два чтения одной строки могут дать разные результаты)
   - По умолчанию в PostgreSQL, Oracle, SQL Server

3. **Repeatable Read (Повторяемое чтение)**:
   - Гарантирует, что данные, прочитанные в транзакции, не изменятся
   - Но возможны фантомные чтения (появление новых строк при повторном чтении)
   - По умолчанию в MySQL InnoDB

4. **Serializable (Сериализуемый)**:
   - Самая строгая изоляция
   - Имитирует последовательное выполнение транзакций
   - Исключает все аномалии параллельного доступа

### Пример транзакции в SQL

```sql
BEGIN TRANSACTION;  -- Начало транзакции

UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE user_id = 2;

COMMIT;  -- Фиксация транзакции
-- или ROLLBACK; для отмены
```

### Проблемы параллельного доступа

1. **Lost Update (Потерянное обновление)**:
   - Две транзакции читают данные, затем обе обновляют их
   - Результат одной транзакции теряется

2. **Dirty Read (Грязное чтение)**:
   - Чтение незафиксированных изменений другой транзакции

3. **Non-repeatable Read (Неповторяющееся чтение)**:
   - Данные изменяются между двумя чтениями в одной транзакции

4. **Phantom Read (Фантомное чтение)**:
   - Появление новых строк между двумя чтениями в одной транзакции

## Подробное описание проблем чтения

### 1. Грязное чтение (Dirty Read)
**Описание**: Транзакция читает данные, которые были изменены другой транзакцией, но еще не зафиксированы.
**Пример**:
```sql
-- Транзакция 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- Пока не COMMIT

-- Транзакция 2 (Read Uncommitted)
BEGIN;
SELECT balance FROM accounts WHERE id = 1; -- Видит незафиксированные изменения
-- Если Транзакция 1 сделает ROLLBACK, Транзакция 2 работала с несуществующими данными
```

### 2. Неповторяющееся чтение (Non-repeatable Read)
**Описание**: В рамках одной транзакции два одинаковых запроса возвращают разные данные из-за изменений, сделанных другой транзакцией.
**Пример**:
```sql
-- Транзакция 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1; -- Чтение 1
-- Другая транзакция изменяет и фиксирует баланс
SELECT balance FROM accounts WHERE id = 1; -- Чтение 2, результат отличается
COMMIT;
```

### 3. Фантомное чтение (Phantom Read)
**Описание**: Появление новых строк (фантомов) при повторном чтении в рамках одной транзакции.
**Пример**:
```sql
-- Транзакция 1
BEGIN;
SELECT COUNT(*) FROM accounts WHERE type = 'savings'; -- 5 записей
-- Другая транзакция добавляет новый savings-аккаунт и COMMIT
SELECT COUNT(*) FROM accounts WHERE type = 'savings'; -- 6 записей
COMMIT;
```

### 4. Потерянное обновление (Lost Update)
**Описание**: Две транзакции читают одни и те же данные, затем пытаются обновить их, и одно из обновлений теряется.
**Пример**:
```sql
-- Транзакция 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1; -- Читает 1000
-- Транзакция 2 тоже читает 1000
UPDATE accounts SET balance = 1000 - 100 WHERE id = 1; -- Пишет 900
COMMIT;
-- Транзакция 2
UPDATE accounts SET balance = 1000 - 200 WHERE id = 1; -- Пишет 800, теряя изменение Транзакции 1
```

## Реализация в популярных СУБД

| СУБД         | Уровень по умолчанию | Особенности реализации |
|--------------|----------------------|------------------------|
| PostgreSQL   | Read Committed       | В Repeatable Read нет фантомов (используется snapshot изоляция) |
| MySQL (InnoDB)| Repeatable Read      | Использует MVCC, предотвращает фантомы с gap locks |
| Oracle       | Read Committed       | Serializable использует snapshot изоляцию |
| SQL Server   | Read Committed       | Поддерживает все стандартные уровни изоляции |

## Как выбрать уровень изоляции?

1. **Read Uncommitted**: Практически не используется, только для специальных задач мониторинга
2. **Read Committed**: Хороший баланс для большинства приложений
3. **Repeatable Read**: Когда важна согласованность данных в рамках одной транзакции
4. **Serializable**: Для критически важных операций, где абсолютная согласованность важнее производительности

## Практический совет

Начинайте с **Read Committed** и повышайте уровень изоляции только при обнаружении проблем. Более высокие уровни изоляции снижают параллелизм и могут привести к увеличению количества блокировок и deadlock'ов.
