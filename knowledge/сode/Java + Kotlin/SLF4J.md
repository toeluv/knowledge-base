В логгерах, таких как SLF4J (который используется в вашем коде), существует специальное правило обработки параметров, которое объясняет этот случай. Вот детальное объяснение:

### Почему работает с одним плейсхолдером и двумя аргументами?

1. **Особенность SLF4J**:
   - Если последний переданный аргумент является исключением (`Throwable`), он не требует плейсхолдера.
   - Такой аргумент всегда обрабатывается особым образом — выводится с полным стектрейсом.

2. **Механика подстановки**:
   ```kotlin
   logger.error("Сообщение: {}", e.message, e)
   //            ↑             ↑        ↑
   //       Шаблон      1-й аргумент  Исключение (спец.обработка)
   ```
   - Первый `{}` заменяется на `e.message`
   - Последний аргумент (`e`) обрабатывается отдельно — добавляет стектрейс

3. **Что будет в логах**:
   ```
   Сообщение: Connection refused  ← e.message
   java.sql.SQLException: Connection refused  ← начало стека
      at example.Test.method(Test.java:12)
      ...
   ```

### Аналогия с перегрузкой методов
Это похоже на перегруженный метод:
```java
// Воображаемая реализация внутри логгера
void error(String msg, Object arg1, Throwable t) {
   String formatted = msg.replaceFirst("\\{}", arg1.toString());
   print(formatted + "\n" + getStackTrace(t));
}
```

### Важные нюансы
1. **Порядок аргументов критичен**:
   ```kotlin
   // Правильно (исключение последнее):
   logger.error("Error: {}", e.message, e)

   // Неправильно (исключение не последнее):
   logger.error("Error: {}", e, e.message) // Стек потеряется!
   ```

2. **Если исключение не нужно**:
   ```kotlin
   // Без стека (явно преобразуем в строку):
   logger.error("Error: {}", "${e.javaClass.simpleName}: ${e.message}")
   ```

3. **Для нескольких плейсхолдеров**:
   ```kotlin
   logger.error("Error in {}: {}", "DB", e.message, e)
   // Заменяются: 1-й {} → "DB", 2-й {} → e.message
   // e → добавляет стек
   ```

### Почему так сделано?
1. **Обратная совместимость** — можно добавить стектрейс, не меняя шаблон.
2. **Удобство** — большинство ошибок требуют и сообщения, и стека.
3. **Производительность** — не нужно парсить шаблон на наличие `{}` для исключения.

Таким образом, это не ошибка, а специальная фича SLF4J для удобного логирования исключений.
Нет, ошибки **не будет**, но поведение изменится в зависимости от типа и порядка аргументов. Разберём возможные случаи на примере SLF4J/Kotlin:

---

### 1. **Корректный вариант (исключение последним)**
```kotlin
logger.error("Ошибка: {}", e.message, e)
```
**Результат**:  
Сообщение + стектрейс.  
Пример лога:
```
Ошибка: Connection refused
java.sql.SQLException: Connection refused
   at example.Test.method(Test.java:12)
```

---

### 2. **Добавление лишнего аргумента (не-исключения)**
```kotlin
logger.error("Ошибка: {}", e.message, "доп.инфо", e)
```
**Что произойдёт**:  
- SLF4J проигнорирует лишний аргумент `"доп.инфо"` (не будет подставлен в `{}`).  
- Исключение (`e`) обработается как обычно (добавит стектрейс).  

**Вывод**:
```
Ошибка: Connection refused
java.sql.SQLException: Connection refused
   at example.Test.method(Test.java:12)
```

---

### 3. **Исключение НЕ последнее (ошибка формата)**
```kotlin
logger.error("Ошибка: {}", e, e.message)
```
**Проблема**:  
- Исключение (`e`) будет преобразовано в строку через `toString()` (без стека!).  
- `e.message` подставится в плейсхолдер `{}`.  

**Вывод** (плохой вариант):
```
Ошибка: java.sql.SQLException: Connection refused
Connection refused  // Это e.message, а не стектрейс!
```

---

### 4. **Передача null вместо исключения**
```kotlin
logger.error("Ошибка: {}", e.message, null)
```
**Результат**:  
- Null обрабатывается как обычный аргумент (не как исключение).  
- Стектрайса не будет.  

**Вывод**:
```
Ошибка: Connection refused
```

---

### 5. **Слишком много плейсхолдеров**
```kotlin
logger.error("Ошибка в {}: {}", "DB", e.message, "лишний", e)
```
**Поведение**:  
- Первые `{}` заменяются на `"DB"` и `e.message`.  
- `"лишний"` игнорируется.  
- Исключение (`e`) добавляет стектрейс.  

**Вывод**:
```
Ошибка в DB: Connection refused
java.sql.SQLException: Connection refused
   at example.Test.method(Test.java:12)
```

---

### Итоговые правила:
1. **Исключение должно быть последним** — иначе стектрейс потеряется.
2. **Лишние аргументы (не-исключения)** — игнорируются, но ошибки не вызывают.
3. **Null вместо исключения** — не приводит к ошибке, но стектрейс не выводится.
4. **Недостаточно плейсхолдеров** — лишние аргументы отбрасываются.

Для явного контроля используйте форматирование строк:
```kotlin
logger.error("Ошибка: ${e.message}\n${e.stackTraceToString()}")  // Полный контроль
``` 

Таким образом, ошибки **не будет**, но логи могут потерять важную информацию, если нарушить порядок аргументов.
