### Конспект: Управление памятью в Java

Java автоматически управляет памятью через сборщик мусора (Garbage Collector), что освобождает разработчика от ручного выделения и освобождения памяти. Однако понимание устройства памяти критически важно для написания эффективного кода и предотвращения утечек памяти.

Память в JVM делится на несколько основных областей.

#### 1. Стек (Stack)

*   **Что хранит:** 
    *   Примитивные типы (int, boolean, double и т.д.), объявленные внутри метода.
    *   Ссылки на объекты (адреса объектов в куче).
    *   Вызовы методов (фреймы стека). Каждый вызов метода создает новый фрейм в стеке, который хранит локальные переменные этого метода.
*   **Как работает:** Работает по принципу LIFO (Last In, First Out — последним пришел, первым ушел).
*   **Кто владеет:** У каждого потока выполнения (Thread) есть свой собственный стек, который не доступен другим потокам.
*   **Время жизни:** Переменная в стеке живет до тех пор, пока не завершится метод, в котором она создана.
*   **Ошибка:** Если стек переполняется (например, из-за бесконечной рекурсии), возникает ошибка `StackOverflowError`.

#### 2. Куча (Heap)

*   **Что хранит:** Все объекты и их поля (атрибуты), а также массивы. Это основная область памяти для динамически создаваемых данных (через оператор `new`).
*   **Кто владеет:** Куча одна на все приложение и разделяется между всеми потоками.
*   **Время жизни:** Объект живет до тех пор, пока на него существуют активные ссылки (пока он используется). После этого он становится кандидатом на удаление сборщиком мусора.
*   **Структура:** Для более эффективной сборки мусора куча логически делится на поколения (см. раздел про GC).

#### 3. String Pool (Пул строк)

*   **Что это:** Это специальная область памяти, расположенная внутри кучи (в Metaspace или в самой куче, зависит от версии Java).
*   **Что хранит:** Уникальные строковые литералы и строки, интернированные методом `intern()`.
*   **Зачем нужен:** Экономия памяти. Благодаря пулу, строки с одинаковым содержанием могут быть представлены одним объектом, на который ссылаются разные части программы.
*   **Как работает:**
    1.  Когда вы создаете строку через литерал (`String s = "Hello";`), JVM сначала проверяет пул.
    2.  Если строка `"Hello"` уже есть в пуле, ссылка `s` будет указывать на существующий объект.
    3.  Если строки нет, создается новый объект в пуле.
    4.  Строки, созданные через оператор `new` (`String s = new String("Hello");`), создают новый объект в куче (вне пула), даже если литерал уже есть в пуле. Чтобы поместить такую строку в пул, нужно вызвать `s.intern()`.

    **Пример:**
    ```java
    String s1 = "Cat"; // Создается в String Pool
    String s2 = "Cat"; // Ссылается на объект из пула
    String s3 = new String("Cat"); // Создается новый объект в куче

    System.out.println(s1 == s2); // true (ссылки на один объект в пуле)
    System.out.println(s1 == s3); // false (ссылки на разные объекты)
    ```

#### 4. Другие области памяти (Metaspace)

*   **Metaspace (ранее PermGen):** Хранит метаданные о классах (информацию о загруженных классах, статические переменные, байт-код методов, константы). Начиная с Java 8, Metaspace использует нативную память (память операционной системы), а не память кучи, что уменьшает вероятность ошибки `OutOfMemoryError`.
*   **Program Counter Register:** Хранит адрес выполняемой в данный момент инструкции.
*   **Native Method Stack:** Стек для нативных методов (написанных на C/C++).

### Как работает Garbage Collector (Сборщик мусора)

GC автоматически удаляет объекты, на которые больше нет активных ссылок, освобождая память в куче.

#### 1. Основные этапы жизни объекта
1.  **Создание:** Объект создается через `new` и помещается в кучу.
2.  **Использование:** На объект есть активные ссылки (например, в стеке или в другом объекте).
3.  **Недостижимость:** На объект больше нет ни одной активной ссылки. Он становится "мусором".
4.  **Сборка:** При следующем запуске GC удаляет объект, если он не был помечен как "живой" (достижимый).

#### 2. Поколенная структура кучи (Generational GC)
JVM использует гипотезу "слабой генерационной гипотезы" (большинство объектов живут недолго). Поэтому куча делится на поколения:

*   **Young Generation (Молодое поколение):**
    *   Создаются все новые объекты.
    *   Делится на: **Eden** (райский сад) и два **Survivor** (выживших) пространства (S0, S1).
    *   **Сборка:** Здесь часто происходит сборка мусора, которая называется **Minor GC**. Когда Eden заполняется, запускается Minor GC. "Живые" объекты перемещаются в один из Survivor-пространств. Счетчик выживаний объекта увеличивается. После нескольких циклов выжившие объекты продвигаются в Old Generation.
*   **Old Generation (Старое поколение):**
    *   Хранит долгоживущие объекты, которые пережили несколько циклов Minor GC.
    *   **Сборка:** Здесь сборка происходит реже, но она дольше, так как область большая. Она называется **Major GC** (или Full GC).
*   **Metaspace:** Очищается от метаданных классов, которые больше не используются (например, при перезагрузке приложений на сервере).

#### 3. Как GC находит "живые" объекты?
Сборщик мусора начинает свою работу с корневых точек (GC Roots) и строит граф достижимости. Все, что не достигнуто обходом от GC Roots, считается мусором.

**GC Roots — это:**
1.  Активные потоки (Threads).
2.  Локальные переменные и параметры методов в стеке (Stack).
3.  Статические переменные классов (в Metaspace).
4.  Ссылки из JNI (Java Native Interface).

#### 4. Типы ссылок
Не все ссылки в Java одинаковы. Тип ссылки влияет на то, когда GC может удалить объект.

1.  **Strong Reference (Сильная ссылка):** Обычная ссылка (`Object obj = new Object()`). Пока есть сильная ссылка, GC никогда не удалит объект.
2.  **SoftReference (Мягкая ссылка):** Объект будет удален только **перед тем, как JVM бросит `OutOfMemoryError`**, если памяти не хватает. Используется для кэшей.
3.  **WeakReference (Слабая ссылка):** Объект будет удален при **ближайшем** запуске GC, независимо от объема памяти. Используется в `WeakHashMap`.
4.  **PhantomReference (Фантомная ссылка):** Объект уже помечен на удаление, но еще не удален. Позволяет узнать момент удаления объекта.

#### 5. Виды сборщиков мусора (кратко)
*   **Serial:** Самый простой, при сборке останавливает все потоки приложения (Stop-The-World). Для клиентских приложений.
*   **Parallel:** Многопоточная версия Serial. Дефолтный в старых версиях. Использует несколько потоков для сборки, но тоже останавливает приложение.
*   **CMS (Concurrent Mark Sweep):** Старался минимизировать паузы, работая одновременно с приложением. Устарел (deprecated) в Java 9, удален в Java 14.
*   **G1 (Garbage First):** Дефолтный GC с Java 9. Делит кучу на регионы, фокусируется на очистке регионов с наибольшим количеством мусора (отсюда название). Балансирует между производительностью и временем пауз.
*   **ZGC и Shenandoah:** Современные низкопаузовые сборщики, стремящиеся сделать паузы менее 10 мс, независимо от размера кучи.

### Итоговая схема памяти

```
        [ Thread Stack ]          [ Thread Stack 2 ]
               |                          |
               | (ссылки на объекты)       |
               ↓                          ↓
        ┌──────────────────────────────────────┐
        │               HEAP (Куча)            │
        │  ┌───────────────┐ ┌──────────────┐  │
        │  │ Young Gen     │ │ Old Gen      │  │
        │  │  Eden  S0 S1  │ │              │  │
        │  └───────────────┘ └──────────────┘  │
        │  ┌────────────────────────────────┐  │
        │  │      String Pool (в куче)      │  │
        │  └────────────────────────────────┘  │
        └──────────────────────────────────────┘
        ┌──────────────────────────────────────┐
        │            Metaspace                  │
        │  (информация о классах, статика)      │
        └──────────────────────────────────────┘
```
